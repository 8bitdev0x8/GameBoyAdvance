## What improved

V48's black stream ran at about 84 kHz and spent about 395 ms/s in its HDMI
handler. V49 returns to the working stream's 31.5 kHz and about 147 ms/s,
while the user confirms visible output. This supports the HSTX restart fix.
The retained windows show no ongoing reset loop. They do not capture every
earlier startup recovery, so a restart counter of five is not zero restarts.

## Where CPU time goes

The latest capture contains five complete, uncontaminated histogram windows
with **12,167 samples**. The partially overwritten earlier window is excluded.
There are zero invalid samples and 195 unmapped samples (1.60%).

| Exclusive core-0 PC sample bucket | Share |
| --- | ---: |
| CPU run/dispatch, including inlined work | 18.30% |
| Native lookup/admission/emission functions combined | **13.87%** |
| Scanline submission/queue handling | 7.69% |
| ARM interpreter | 5.79% |
| General bus reads | 4.87% |
| Native timing/fetch gate | 4.10% |
| Generated native machine-code body | **0.73%** |

The compiler bucket includes `try_run_native` (7.76%) and emitter methods
(6.11%). Compiler ROM peeks, memory utilities and bus work have their own
PC buckets, so that combined percentage does not include every compilation
cost. Generated-body samples do not include its timing/memory helpers.
These are sampled shares of the interrupted core-0 thread; the higher-priority
HDMI handler is timed separately. Do not add these shares to IRQ wall-time
percentages or interpret an inlined dispatcher bucket as dispatch alone.

This strongly suggests that compilation, short native calls and limited code
reuse are expensive. It does **not** directly prove an eviction rate or that
disabling translation would be faster. A native-on/off same-scene comparison
and cache counters are still needed.

The executable cache has a **2,304-byte pool and 16 descriptors**. A generated
block can approach 1 KiB; the pool therefore cannot retain 16 worst-case blocks.
The admission table also shares hotness across neighboring PCs in a 64-byte
region, so it does not measure exact-PC heat. These are concrete design points
to examine before expanding the translator.

## Next substantial changes to evaluate

1. **Measure translation reuse.** Record compilation attempts/successes,
   hits/misses, evictions, generated bytes, executed guest instructions and
   native calls as interval counters. This separates frequently recompiled
   code from many cold entries and expensive tiny blocks.
2. **Retain profitable code.** Use exact-PC admission and a replacement policy
   based on actual reuse. Evaluate a PSRAM backing cache for already-emitted
   blocks, promoting active blocks into executable SRAM. PSRAM capacity is
   tight: budget any backing tier explicitly, potentially by reclaiming a few
   ROM-cache pages and measuring the resulting decompression misses. Do not
   consume the remaining internal heap blindly.
3. **Increase useful execution per entry.** Profile unsupported opcode classes
   and exit reasons, then extend the common boundaries and chain hot blocks.
   Longer blocks alone do not eliminate service, DMA, interrupt or slice
   deadlines. Guest event timing and native/interpreter parity must remain
   correct.
4. **Reduce remaining CPU/bus work.** Keep cheap eligibility rejection ahead
   of expensive translator work, and target fetch/memory paths supported by
   profiles. CPU dispatch remains the largest single sampled bucket.
5. **Continue renderer optimization after those CPU changes.** Background
   drawing and mixing average 5.75 and 5.61 ms/frame on core 1. Almost all
   explicit CPU render waiting is queue-full waiting, rather than video-write
   barriers. Copy is already effectively zero.

Holding all other work fixed, removing all 7.22 ms of explicit renderer wait
would move this window from 10.56 to only **11.44 FPS**. That arithmetic is
not a prediction of a real renderer change. Run, Draw and IRQ timing overlap;
they must not be summed. Achieving 60 FPS requires much more than eliminating
render waits or compilation alone.

## Which additional parameters help

Prefer bounded counters captured once per frame or per one-second window:

- Cache lookup hits/misses, compile attempts/failures, evictions and code bytes.
- Native guest instructions/calls, interpreted ARM/Thumb counts and average
  instructions per native call, with instruction-counting overhead measured.
- Exit counts for unsupported opcodes, deadline/service boundary, DMA, IRQ and
  changed code; count exits rather than logging every gate invocation.
- Memory reads/writes by region, measured in a separate diagnostic trial when
  needed; avoid burdening all bus accesses in the normal performance build.
- Separate core-1 idle time from jobs, plus queue depth and existing BG/mix phases.

Store unsigned interval deltas in the existing binary logging scheme. Avoid
per-instruction text output and instrument one hypothesis at a time. Existing
USB `native status` provides cumulative translator counters, but V49 frame
records retain only the native-enabled flag; they cannot reconstruct interval
compile/eviction rates. These additions and the cache redesign are **not yet
implemented in V49**.

The reproducible decoded report is `output/log-analysis-v49.json`. V49 firmware
and its immutable package summary are retained; no new firmware or FPS gain
is claimed by this analysis.
